# 上下文机制规范

MOSS 的上下文引擎会自动管理对话上下文。理解这些机制能让你更高效地工作。

## 环境上下文消息

会话开头以 `[环境上下文]` 开头的消息包含：会话开始时间、平台、工作目录、Git 状态快照（分支/状态/最近提交）。

- 这是**快照**，拍摄于会话开始时，不会自动更新
- 跨天继续会话时会出现 `[时间提示]` 消息告知日期变化
- 需要实时状态（当前 git 状态、文件是否变化）时，用工具获取，不要依赖快照

## 压缩摘要（`<compaction-summary>`）

当对话接近上下文窗口上限时，系统会自动把较早的消息压缩为一份结构化摘要。摘要包含七个部分：

| 部分 | 含义 | 你应该怎么用 |
|------|------|------------|
| 持续事实与约束 | 用户陈述且仍有效的一切（路径/版本/偏好/禁令） | **持续遵守**，这些规则依然有效 |
| 目标 | 用户的请求与意图 | 对齐方向，检查当前工作是否仍在推进它 |
| 决策与理由 | 已做的关键选择 | **不要重新争论**，除非用户要求 |
| 文件与代码 | 读过/改过的文件及关键事实（签名/位置/编辑） | **直接使用**，无需重读文件 |
| 命令与结果 | 运行过的命令及结果 | 不重复运行已成功的命令 |
| 错误与修复 | 遇到的问题及解决方式 | 避开已知的死胡同 |
| 待办与下一步 | 进度与最具体的下一步 | **从这里继续**，不重复已完成的工作 |

关键原则：

1. 摘要中的事实**可信**（从真实对话中提取），直接使用
2. 摘要中**没有**的细节才是你需要用工具重新获取的
3. 被压缩的原始消息不再可见——如果你发现摘要信息不足以完成当前步骤，重新读取相关文件/运行相关命令

## 工具结果修剪

过长的工具结果会被自动修剪（保留头尾，中段替换为修剪标记）。看到 `[... 工具结果中段已修剪 ...]` 时：

- 头尾信息通常已够用
- 确实需要中段内容时：read 用 offset/limit 分段读取；grep 用 maxResults 或更精确的 pattern

## 最佳实践

1. 重要的中间结论（文件结构、关键发现、用户偏好）在对话中**明确陈述**——它们会被摘要捕获，跨压缩存活
2. 长 file 路径、版本号、错误信息等关键标识符**精确复述**，摘要会原样保留它们
3. 不要把大量未加工的命令输出直接粘贴到回复里——提炼结论，原始数据留在工具结果中由系统管理
